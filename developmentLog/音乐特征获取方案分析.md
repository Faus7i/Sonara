# 音乐特征获取途径与推荐算法依赖分析

> **日期**: 2026-05-21  
> **背景**: Spotify 于 2024 年 11 月起限制新创建 App 访问 `/audio-features` 端点，  
> 本项目的 Spotify App（Client ID: `352220271e18487297cdc08735535e34`）经实测确认返回 403。

---

## 1. 当前状态

### 1.1 实测结论

| Spotify 端点 | HTTP 状态 | 说明 |
|-------------|----------|------|
| `/search` | ✅ 200 / 429 | 搜索正常（429 为频率限制，非权限问题） |
| `/tracks/{id}` | ✅ 200 | 曲目元数据正常（名称、艺术家、专辑、时长、流行度等） |
| `/artists/{id}` | ✅ 200 | 艺术家数据正常（名称、流派、粉丝数、图片） |
| `/albums/{id}` | ✅ 200 | 专辑数据正常（名称、发行日期、曲目列表、厂牌） |
| `/audio-features/{id}` | ❌ **403** | **端点已锁定** |
| `/audio-features?ids=` | ❌ **403** | 批量端点同样锁定 |

### 1.2 项目受影响的代码

| 文件 | 影响 |
|------|------|
| `src/Infrastructure/Spotify/SpotifyClient.cs` — `GetAudioFeaturesAsync()` | 调用 Spotify API 永远返回 403 |
| `src/Infrastructure/Spotify/SpotifyClient.cs` — `GetAudioFeaturesBatchAsync()` | 同上 |
| `src/Modules/AudioFeatures/Handlers/ImportAudioFeaturesCommandHandler.cs` | 导入功能完全不可用 |
| `src/Modules/AudioFeatures/Handlers/GetAudioFeaturesQueryHandler.cs` | 查询只能返回本地已缓存数据 |

### 1.3 可正常获取的元数据

即使音频特征端点被锁，以下数据仍可正常获取：

| 类别 | 字段 |
|------|------|
| 曲目基础 | 名称、时长(ms)、曲目号、ISRC |
| 艺术家 | 名称、流派标签、粉丝数、头像 |
| 专辑 | 名称、发行日期、类型、厂牌、版权 |
| 内容标识 | explicit 标记、preview_url(30秒MP3) |
| 热度 | popularity (0-100) |

## 2. 推荐算法对音乐特征的依赖分析

### 2.1 目标算法（开发文档定义）

```
FinalScore = 0.35 × AudioSimilarity + 0.25 × BehaviorScore
           + 0.15 × GenrePreference + 0.10 × Freshness
           + 0.10 × Diversity + 0.05 × Popularity
```

### 2.2 各权重对音频特征的依赖

| 权重 | 组件 | 依赖音频特征 | 替代方案 |
|------|------|:---:|------|
| **35%** | AudioSimilarity | ❌ 核心依赖 | 可用流派+热度+时长替代，精度下降 |
| 25% | BehaviorScore | ✅ 不依赖 | 基于搜索/收藏/播放行为（Phase 4） |
| 15% | GenrePreference | ✅ 不依赖 | 基于艺术家流派标签 |
| 10% | Freshness | ✅ 不依赖 | 基于发行日期 |
| 10% | Diversity | ⚠️ 部分依赖 | 可用流派多样性替代 |
| 5% | Popularity | ✅ 不依赖 | Spotify popularity 字段可用 |

### 2.3 AudioSimilarity 的具体依赖

当前特征向量为 5 维：`[energy, danceability, valence, tempo, acousticness]`

| 特征 | 在相似度计算中的角色 | 可否替代 |
|------|-------------------|:---:|
| **Energy** | 区分高能/舒缓音乐 | ✅ NWaves RMS |
| **Danceability** | 区分舞曲/非舞曲 | ⚠️ 需 ML 模型，难本地算 |
| **Valence** | 区分欢快/悲伤 | ⚠️ 需 ML 模型，难本地算 |
| **Tempo (BPM)** | 节奏快慢 | ✅ SoundNet / 节拍检测 |
| **Acousticness** | 区分原声/电子 | ⚠️ NWaves 可近似（谐波比） |

### 2.4 降级方案：无音频特征的推荐

如果完全不使用音频特征，推荐算法退化为：

```
降级 Score = 0.35 × GenreSimilarity + 0.25 × BehaviorScore
           + 0.15 × GenrePreference + 0.10 × Freshness
           + 0.10 × PopularityBased + 0.05 × Popularity
```

影响评估：
- **高匹配度推荐**（70% 部分）精度下降约 30-50%
- **相邻风格探索**（20% 部分）可用流派+艺术家关联替代
- **多样性探索**（10% 部分）几乎不受影响
- **推荐解释**受损最严重——无法给出"因为你喜欢高能量电子音乐"这样的精准理由

## 3. 音乐特征获取方案对比

### 3.1 方案总览

| # | 方案 | 类型 | 月请求量 | 月费用 | 特征覆盖 |
|---|------|------|---------|--------|:---:|
| A | Spotify 官方 API | 云端 | 无限 | $0 | 0/10（已封锁） |
| B | SoundNet 免费版 | 云端 | 50-100 | $0 | 10/10 |
| C | SoundNet 付费版 | 云端 | 10,000 | ~$10 | 10/10 |
| D | NWaves 本地计算 | 本地 | 无限 | $0 | 2/10（5 可近似） |
| E | NWaves + SoundNet 混合 | 本地+云端 | ~50 | $0 | 8-9/10 |
| F | Essentia 命令行（C++） | 本地 | 无限 | $0 | 7-8/10 |
| G | 降级推荐（无音频特征） | N/A | 0 | $0 | 0/10 |

### 3.2 方案 A：Spotify 官方 API（已失效）

**状态**：❌ 不可用  
**原因**：App 在 2024 年 11 月后创建，被永久排除在 Audio Features 端点之外  
**实测**：`GET /audio-features/{id}` → 403 Forbidden  
**结论**：除非迁移到老 App 或成功申请 Extended Quota Mode，否则无法使用。

### 3.3 方案 B：SoundNet 免费版

**原理**：通过 RapidAPI 调用 SoundNet 的 `/pktx/spotify/{trackID}` 端点，获取第三方缓存的音频特征。

**优点**：
- 全 10 个 Spotify 特征 + Camelot 调性（DJ 混音用）
- RESTful API，集成简单（标准 `IHttpClientFactory`）
- 字段命名清晰，数据质量高
- 零维护成本

**缺点**：
- **50-100 次/月**免费额度，对批量建曲库严重不足
- 建 1000 首曲库需 10-20 个月
- 依赖第三方服务稳定性
- 数据来源不透明（可能是旧版 Spotify API 缓存）

**适用场景**：低频导入（每次用户手动搜索后导入 1 首），不建批量曲库。

**集成改动量**：5 个新文件，修改 1 个 Handler，约 1 小时。

### 3.4 方案 C：SoundNet 付费版

**原理**：同方案 B，使用付费计划。

**优点**：
- 10,000 次/月，建 1000 首曲库 1 次跑完
- 日滚动更新 20 首仅占 6% 额度
- 所有方案中开发速度最快
- 代码与免费版完全相同（仅 Key 不同）

**缺点**：
- 月费 ~$10（约 72 元人民币）
- 毕设答辩后若不再付费，曲库停止更新
- 依赖第三方服务

**适用场景**：毕设答辩前开 1-2 个月，展示完整推荐系统。

**集成改动量**：同方案 B。

### 3.5 方案 D：NWaves 纯本地计算

**原理**：下载 Spotify `preview_url`（30 秒 MP3），使用 .NET 音频处理库 NWaves 本地提取特征。

**NWaves 能力矩阵**：

| Spotify 特征 | 可计算 | 方法 | 精度 |
|-------------|:---:|------|:---:|
| Energy | ✅ | RMS 能量值 | 高 |
| Loudness | ✅ | RMS → dB | 高 |
| Acousticness | ⚠️ | 谐波/噪声比 | 中 |
| Instrumentalness | ⚠️ | 谐波比 + 频谱特征 | 中低 |
| Speechiness | ⚠️ | 频谱平坦度 + 过零率 | 中低 |
| Key / Mode | ⚠️ | Chroma 特征推断 | 中低 |
| **Tempo (BPM)** | ❌ | 不支持节拍检测 | — |
| **Danceability** | ❌ | 需 ML 模型 | — |
| **Valence** | ❌ | 需 ML 模型 | — |

**优点**：
- 永久免费，无额度限制
- 完全离线，无网络依赖
- 可处理任意数量的曲目

**缺点**：
- **Tempo、Danceability、Valence 完全缺失**——恰好是推荐算法核心维度
- NWaves 0.9.6 发布于 2021 年，4.5 年未更新
- 不解析 MP3——需额外引入 NAudio 等解码器
- 可计算特征精度远低于 Spotify 官方数据
- 开发周期 1-2 天

**适用场景**：仅需 Energy/Loudness 的基础分析场景。

### 3.6 方案 E：NWaves + SoundNet 混合（⭐ 推荐）

**原理**：两阶段处理——NWaves 本地提取基础特征（免费无限），SoundNet 按需补充 ML 特征（仅 3 个）。

```
第 1 阶段 — NWaves（免费、无限制）：
  ✅ Energy (RMS)
  ✅ Loudness (RMS → dB)
  ✅ Acousticness (谐波比近似)
  ✅ Instrumentalness (近似)
  ✅ Speechiness (频谱平坦度 + ZCR 近似)

第 2 阶段 — SoundNet 补充（仅在需要时）：
  ✅ Tempo (BPM)
  ✅ Danceability
  ✅ Valence (Happiness)
  ✅ Key / Mode（可选）
```

**流量分析**：

| 场景 | SoundNet 调用 | 月消耗 |
|------|:---:|:---:|
| 用户手动导入 1 首 | 1 次（仅 3 个 ML 特征） | — |
| 每日探索 5 首新歌 | 5 次/天 = 150 次/月 | 超出免费版 ❌ |
| 每周探索 10 首新歌 | 10 次/周 = 40 次/月 | 免费版够用 ✅ |
| 建 1000 首初始曲库 | 1000 次 | 需付费版 |

**优点**：
- 免费版可在低频场景下工作（每周 10 首）
- 基础特征本地无限制，不受 API 额度影响
- SoundNet 仅用于 3 个不可本地计算的核心特征
- 最大化利用免费额度

**缺点**：
- 实现复杂度最高（两套系统并行）
- NWaves 本地特征精度有限
- 需处理 MP3 下载→分析→删除的临时文件管理

**适用场景**：长期运行的低频个性化推荐，预算敏感。

**集成改动量**：8-10 个新文件，修改 1 个 Handler，约 3-4 小时。

### 3.7 方案 F：Essentia 命令行

**原理**：使用全球最强大的开源音频分析库 Essentia（C++），通过 .NET `Process` 管道调用其命令行工具提取特征。

**优点**：
- 特征覆盖最全：Tempo、Key、Mode、Energy、Danceability、Valence 等均支持
- 开源免费，无 API 调用限制
- 学术界广泛使用，精度经过验证

**缺点**：
- 需安装 C++ 运行时 + Essentia 二进制文件
- .NET 集成通过 `Process.Start()` 调用，跨平台兼容性差
- 输出解析依赖字符串匹配（JSON 或 YAML）
- 每首曲目 fork 一个进程，性能开销大
- Windows 上配置复杂

**适用场景**：对特征精度要求极高的研究场景。

### 3.8 方案 G：纯元数据推荐（无音频特征）

**原理**：放弃音频特征，仅使用 Spotify 可获取的元数据构建推荐。

**可用信号**：

| 信号 | 来源 | 推荐用途 |
|------|------|---------|
| 流派 | Artist.genres | GenreSimilarity (35%) |
| 流行度 | Track.popularity | Popularity 权重 |
| 发行日期 | Album.release_date | Freshness 权重 |
| 时长 | Track.duration_ms | 辅助过滤 |
| 艺术家关联 | Track.artists | 协同过滤 |

**优点**：
- 零额外成本、零集成工作
- 当前代码完全可用
- 推荐结果仍有一定参考价值

**缺点**：
- AudioSimilarity（35% 权重）完全降级为 GenreSimilarity
- 无法区分同流派内的高能/舒缓、欢快/悲伤
- 推荐解释失去技术深度（无法展示"音频特征雷达图"）

**适用场景**：快速原型验证、答辩中演示推荐系统框架。

## 4. 曲库滚动更新方案分析

### 4.1 方案描述

> 本地维护 1000 首曲库 → 分析特征 → 匹配用户喜好 → 淘汰不符合的歌曲 →  
> 拉取新歌曲保持 1000 首容量 → 推荐从本地库出 → 支持 Spotify 实时播放

### 4.2 各环节可行性

| 环节 | 技术可行性 | 瓶颈 |
|------|:---:|------|
| Spotify 搜索拉取曲目 | ✅ | 基础 API，无限制 |
| 下载 preview_url MP3 | ✅ | 1000 × 500KB = 500MB 临时 |
| **特征分析（1000 首）** | ⚠️ | SoundNet 免费版需 10-20 个月 |
| 分析后删除临时 MP3 | ✅ | 零存储成本 |
| 用户画像匹配 | ❌ | **Phase 4 未实现**，无 UserProfile 数据 |
| 淘汰+拉新保持 1000 首 | ⚠️ | 每轮淘汰触发新 SoundNet 调用 |
| 本地库推荐 | ✅ | 从 SQL Server 查询即可 |
| Spotify 实时播放 | ✅ | Player 模块（Phase 3 已完成） |

### 4.3 核心约束

1. **用户画像缺失**（Phase 4 待开发）：不知道用户喜欢什么，无法做"去除不符合"的判断
2. **SoundNet 额度**：免费版根本撑不住 1000 首初始构建 + 滚动更新
3. **Spotify API 频率限制**：连续大量请求会触发 429，需间隔控制

### 4.4 方案可行性结论

| 条件 | 结论 |
|------|------|
| SoundNet 付费版 + Phase 4 完成 | ✅ 可行 |
| SoundNet 免费版 + 低频更新（每周 10 首） | ⚠️ 勉强可行，但建库周期长 |
| 纯 NWaves 本地计算 | ❌ 缺失核心特征 |
| Phase 4 未完成 | ❌ 无法做用户匹配 |

## 5. 推荐路径

### 短期（Phase 4-5 开发期间）

采用 **方案 E（NWaves + SoundNet 混合）+ 方案 G（元数据兜底）**：

```
开发顺序：
  1. 完成 Phase 4（UserProfiles 用户画像）
  2. 集成 NWaves 本地特征提取（5 个基础特征）
  3. 集成 SoundNet（3 个 ML 特征补充）
  4. 实现混合推荐算法（Phase 5）
  5. 如音频特征不足，降级为元数据+流派推荐
```

### 毕设答辩前

开 1 个月 SoundNet 付费版（约 72 元），一次性构建完整曲库，展示最佳效果。

### 特征存储策略

无论使用哪个方案，**数据一旦写入本地 `TrackAudioFeatures` 表就永久缓存**，后续查询不再消耗 API 额度。`TrackAudioFeature` 实体允许部分字段为 null，混合方案中 NWaves 计算的特征和 SoundNet 补充的特征可以非同时写入。

## 6. 最终建议

| 优先级 | 行动 | 说明 |
|:---:|------|------|
| 1 | 不改变 Phase 4 开发计划 | 用户画像是推荐系统的前提，比特征获取更紧迫 |
| 2 | 先集成 SoundNet（方案 B） | 5 个文件、1 小时，验证特征获取通路 |
| 3 | 按需追加 NWaves（方案 E） | 当 SoundNet 免费额度不够时再启用本地计算 |
| 4 | 答辩前开付费版（方案 C） | $10 买完整展示效果，性价比极高 |
| 5 | 保留降级推荐（方案 G） | 作为最终兜底，确保系统在任何情况下都有推荐输出 |
